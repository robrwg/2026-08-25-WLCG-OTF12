Full definitions, spoken (trimmed off the slide for the 40-word rule): an agent uses an LLM to decide a step, call a TOOL, read the result, repeat. An MCP server (Model Context Protocol) is a standard adapter exposing a service (Rucio, a notebook, a DB) as tools plus live context any agent can call. A skill is STATIC context loaded on demand, a reusable recipe ("how we do a fit here"). A runtime is the app that gives the agent hands: runs commands, wires MCPs, enforces permissions (Claude Code, Codex, ...). A discoverable collection of plugins is a marketplace. Keep FAST — the OTF room is technical but not uniformly agent-literate. 60–90 s max. "Runtime" is the deliberate word choice; say once that the AI engineering community also says "harness" and move on. Timing: main-line but compressible.

PR-gated: autonomous vs human-required.

AI drafts → expert reviews → merged. The PR is the audit record.

Card detail, spoken: principles are immutable commitments (human-in-the-loop UNTIL TRUST IS EARNED); policies are scoped YAML derived from them ("wait for human ack after restart"); a runbook is a human-reviewed, PR-gated spec per capability — what it does, what it may do autonomously, what requires a human. The full loop: AI drafts from cluster ground truth, the domain expert reviews and corrects, merged = blessed, runbook + agent config = a deployed capability. The tools sysadmins already trust — git, code review, PRs — become the trust machinery for agents. Nothing exotic: a principle is a value, a policy is that value made specific to one service, a runbook is the contract for one capability. The runbook is deliberately the atomic unit of trust: an action type is either listed as autonomous or it requires a human, and changing that list is itself a PR. Say out loud: "if you can review a colleague's change, you can review an agent's charter." This and the next two slides are the concepts behind our UChicago implementation; the framework names are deliberately left off — the concepts are what port.

Card detail, spoken: L1 = AI drafts runbooks and diagnoses, no autonomous action; L2 = agents act for a physicist with that user's credentials only, no admin access ever; L3 = scheduled agents, scoped service accounts, read-only defaults, explicit write allowlists, PR-gated changes. The callout's cut tail: governance level = what it may do, environment = where; the framing is blast radius, not compliance. Environment stair: dev proves the pattern, staging proves it under load. Level 1 is where every site can start tomorrow: AI-assisted runbook writing, humans at the keyboard. Level 2 is the physicist story from Part 2 — the agent holds the user's own credentials and nothing more, so the worst case is what that user could already do. Level 3 is the interesting one for this room: scheduled, privileged automation, made tolerable by scoped service accounts, read-only defaults, explicit write allowlists, and PR-gated promotion. The environment progression is mandatory at our site: a dev sandbox cluster, then a staging cluster, then the AF — patterns are proven twice before they touch production. Say: "the question we ask is never 'is it smart enough' but 'what is the blast radius if it is wrong.'"

Card detail, spoken: normative source = runbooks, policies, agent configs; runtime state record = accumulated knowledge + daily session logs, auto-pushed to git, human-reviewed; DR archive = daily snapshots of agent state and conversations, restart = restore + wait for human ack; session memory = live in-process state, lost on crash, and that's fine. This is the answer to "how would I even know what it's doing?" — the question every experienced admin asks first. Two distinctions to say out loud: runbooks are read-only and procedural (what it CAN do); memory is read-write and experiential (what it HAS learned) — a window into the running agent's mind, in git, diffable, reviewable at the weekly ops meeting like any other change. The promotion loop is the payoff: the agent's operational experience flows back into the human-owned runbook only through review. And the trust escalation log is the single most quotable governance idea we have: autonomy changes are themselves version-controlled — you can point to the commit where you stopped watching, who approved it, and on what evidence. Frame CIMD as "a newer proposal worth watching," not "the standard." AARC/WLCG line matters for Groep/Campana in the room. Deep-dive · CIMD vs DCR

Client ID = a URL the server fetches

GET /authorize?client_id=https://app.example/oauth.json&…
        │  authn server fetches the JSON, validates, applies policy
        ▼
{ "client_id":"https://app.example/oauth.json",
  "client_name":"…","redirect_uris":[…] }   ← hosted by the client
  • Wins: no /register abuse; stable identity; domain allow/deny.
  • Costs: outbound fetches (SSRF); localhost ambiguity; domain ≠ trust.
Auth today reuses grid creds (x509) or Keycloak OIDC — OAuth bridge docs.
BACKUP. Cut from the slide: SSRF mitigations (block private IPs, HTTPS-only, size/timeout caps), and the concrete FastMCP knob — CIMDTrustPolicy(trusted_domains=["claude.ai", "cursor.com"], auto_approve_trusted=True): the facility decides which domains skip consent. The client_id IS the HTTPS URL to a metadata doc the client hosts; the authn server fetches it on demand, validates client_id == source URL and the redirect_uris, then applies its own policy. Read-only, stateless, fetch-on-demand. Spec status: adopted into MCP 2025-11-25 via SEP-991, from an IETF draft promoted to WG status Oct 2025 (origins in IndieAuth; in production at Bluesky); MCP Python SDK added minimal client-side support in v1.23.0, server-side still maturing. Stance: CIMD = SHOULD, DCR = MAY, pre-registration still allowed. Software statements (RFC 7591 §2.3) / OS attestation are the next layer if asked.
